**Status:** `experiments/04_lora_finetuning/README.md`'s "Report tables" section now documents these 5 real files. `scripts/run_registry.json`'s `workbook` fields still point at the three never-produced files, and `export_finetuning_report.py` + `sheet_builders.py` + `metrics_parser.py` still implement that dead pipeline — these are now flagged in the README as legacy/unused rather than deleted outright.

- **Status: all 5 current files are now fully script-generated** (`fill_good_vs_bad_gpt.py`, the last partial one, has been removed and replaced by `compare_leakage_honesty_check_to_excel.py`, §3). **Still open:** decide whether to delete `export_finetuning_report.py`/`sheet_builders.py`/`metrics_parser.py`/the stale `workbook` fields in `run_registry.json` outright, or leave them as-is (these were superseded, not replaced, by the new scripts).
  - Building `compare_epochs_to_excel.py` surfaced a `run_registry.json` gap: the registry had no entry for the `qwen_lora_no_few_shots` folder (1 epoch, zero-shot) that `epoch_ablation.xlsx`'s "1 epoch" column actually uses — only the few-shot 1-epoch run was registered. **Fixed:** added an entry for that folder (now `lora_1_epoch_zero_shot` after the naming standardization below), `use_few_shot: false`, `num_epochs: 1`, for both 3B and 7B; the script selects runs by `use_few_shot == false` at each epoch count so it doesn't silently pick the few-shot variant.
  - Building `compare_few_shots_to_excel.py` surfaced two data bugs in the old hand-assembled `few_shots_ablation.xlsx` (3B sheet only): the `qwen_base` block's `enes`/`enru` term-accuracy values were swapped between rows, and both the `qwen_base` and `qwen_lora` blocks' 3rd row was labeled `ende` instead of `enru` (values were correct in the `qwen_lora` block — label-only typo there; the `qwen_base` block had the actual value swap). **Fixed** — the generated file derives each row directly from `metrics_summary.json` per language, so this can't recur. Also found the old file's `enes` Term Acc cell (75.47) was a copy-paste duplicate of the adjacent chrF cell, not real data — moot now since the generated file derives every value from `metrics_summary.json` directly.

## 3. Undocumented or partially-documented experiments

- **Data-leakage honesty check** (see `README.md` §3.4.2 for the full reconstruction) — not mentioned in any README anywhere in the repo (still true of the underlying methodology, though the workbook itself is now documented). Formerly `good vs bad data.xlsx` (a single 5-block sheet, partly `fill_good_vs_bad_gpt.py`-generated, partly hand-entered); redesigned into `leakage_honesty_check.xlsx`, fully generated by `compare_leakage_honesty_check_to_excel.py`. Went through several rounds: 2 sheets -> 1 consolidated sheet (`overlap_vs_no_overlap_data`) with 3 stacked model blocks (`qwen_base`, `gpt`, `qwen_lora`); `bad_data`/`good_data` columns renamed to `overlap_data`/`no_overlap_data`.
  - **New finding:** the two subsets are confounded with sentence length/terminology density, not just training-set overlap. Measured directly from `data/test_cleaned_by_sentences/{data_bad,data_good}/*.jsonl`: `overlap_data` sentences are 30-49% shorter on average across all 3 language pairs (e.g. `enes`: 8.6 vs 17.0 words), while per-sentence term counts are nearly flat (~2.1-2.5 both ways) and total unique terms per subset are nearly identical (e.g. `ende`: 179 vs 191) -- so `overlap_data` has notably higher terminology density (most pronounced on `enes`: 38.8% vs 17.8%). This explains why even GPT (never trained on dev_v2) shows a real overlap-vs-no-overlap gap; see `report/README.md` §3.4.2 for the full write-up.
  - **Bug found and fixed:** `fill_good_vs_bad_gpt.py`'s Qwen-base block used to wire `good_path` to the plain, unfiltered `qwen_base/metrics_summary.json` instead of a real good-filtered subset. Investigating this while building the new script found `qwen_base/test_cleaned_by_sentences/data_good/metrics_summary.json` already exists and its numbers already matched the old file's — so the bug's practical impact was already resolved upstream (the "bad vs full-unfiltered" scenario no longer occurs); `fill_good_vs_bad_gpt.py` itself has been deleted since it's fully superseded.
  - Only 2 of 5 comparison blocks (GPT, Qwen-base) are script-generated; the 3 `qwen_lora` blocks have no generating script anywhere and appear hand-entered.
  - Only evaluated for Qwen **7B**; no 3B good/bad results exist.
  - `filter_test_sentence_overlap.py` / `filter_test_term_overlap.py` both default to output directories (`data/test_cleaned_gpt`, `data/test_cleaned`) that don't match the actually-committed directories (`test_cleaned_by_sentences/`, `test_cleaned_by_terms/`) — as committed, neither script reproduces the current data without manually passing `--output-dir`.
  - `filter_test_term_overlap.py` overwrites its input file in place (per subagent investigation) — re-running it destructively modifies source data rather than writing a fresh copy, unlike its sentence-level sibling.

- **`test_cleaned_by_terms` split prepared but never evaluated**, and turns out heavily skewed once inspected: 11–14 "good" sentences vs. 483–486 "bad" sentences per language (nearly every dev_v1 sentence shares a term-dictionary entry with dev_v2 training data). No `results/.../test_cleaned_by_terms/` directory exists anywhere.
  - **Recommendation:** don't run it — note the skew as the reason it wasn't used, rather than silently omitting it.

- **Few-shot is split across two independently-produced, inconsistently-named result trees**, unified only inside `experiments/04_lora_finetuning/scripts/figure_lora_finetuning.py`:
  1. Baseline-level: `results/dev_v1/original/{zero_shot,few_shot}/` (repo root, renamed from `{no-few-shots,with-few-shots}/`) — GPT + Qwen 3B/7B, no fine-tuning. **Status: fixed** — both subfolders now consistently use `qwen_3b`/`qwen_7b` (underscore); `zero_shot/` (formerly `no-few-shots/`) previously used `qwen-3b`/`qwen-7b` (hyphen). Internal directory shape still differs between the two (unrelated, not fixed here).
  2. LoRA-level: `run_registry.json`'s `lora_1_epoch_few_shot` is the only few-shot LoRA run; all multi-epoch runs are zero-shot — so on the LoRA side, "few-shot effect" and "epoch count" are confounded. There is no `lora_2_epoch_few_shot`/`lora_3_epoch_few_shot` to isolate them.
  3. ~~**`run_registry.json`'s `use_few_shot: false` for both Qwen base runs is itself wrong**~~ — ✅ fixed: the actual base runs used 3 few-shot examples per language, but the registry said `false`. The flag is now `true` and the run id renamed `base_few_shot`.
  - **Fix:** decide (see §6) whether to invest in the missing `lora_2_epoch_few_shot`/`lora_3_epoch_few_shot` runs or explicitly describe the confound as a limitation (still open).

  - **Fix going forward:** either script-generate every cell (write the missing `qwen_lora` block generator) or clearly flag hand-edited sheets/cells (e.g. a header note or a distinct fill color) so a reader — or the report writer six months later — can tell which numbers are traceable to a script run and which aren't.
