## 2. `04_lora_finetuning`'s README documents a pipeline that doesn't exist — ✅ fixed (README rewritten)

`experiments/04_lora_finetuning/README.md` used to describe an Excel export producing three workbooks — `results_Qwen2.5-3B.xlsx`, `results_Qwen2.5-7B.xlsx`, `results_GPT4o-mini.xlsx` — each with a specific documented sheet set (`main_results`, `base_vs_lora`, `epoch_ablation`, `experiment_config`, `training_loss_meta`, `training_loss`, etc.). **None of these three files ever existed in the repo.** The old committed workbook, `comparisons.xlsx`, had a completely different, partly-hand-filled sheet set — and has since been deleted and replaced by 5 purpose-named files (`good vs bad data.xlsx`, `base_few_shots_vs_lora_1_epoch.xlsx`, `best_models.xlsx`, `epoch_ablation.xlsx`, `few_shots_ablation.xlsx`), mirroring the one-file-per-comparison convention used in `experiments/01`–`03`.

**Status:** `experiments/04_lora_finetuning/README.md`'s "Report tables" section now documents these 5 real files. `scripts/run_registry.json`'s `workbook` fields still point at the three never-produced files, and `export_finetuning_report.py` + `sheet_builders.py` + `metrics_parser.py` still implement that dead pipeline — these are now flagged in the README as legacy/unused rather than deleted outright.

- **Still open:** decide whether to delete `export_finetuning_report.py`/`sheet_builders.py`/`metrics_parser.py`/the stale `workbook` fields in `run_registry.json` outright, or leave them as-is. Separately, 2 of the 5 current files (`base_few_shots_vs_lora_1_epoch.xlsx`, `best_models.xlsx`) still have no generating script at all (hand-assembled) — writing scripts analogous to `experiments/03_dataset_comparison/scripts/compare_datasets_to_excel.py` (or this experiment's own `scripts/compare_epochs_to_excel.py`/`scripts/compare_few_shots_to_excel.py`) would remove that manual-copy risk before the paper cites their numbers.
  - Building `compare_epochs_to_excel.py` surfaced a `run_registry.json` gap: the registry had no entry for the `qwen_lora_no_few_shots` folder (1 epoch, no few-shot) that `epoch_ablation.xlsx`'s "1 epoch" column actually uses — only `lora_1ep_fs` (folder `qwen_lora`, few-shot) was registered for 1 epoch. **Fixed:** added a `lora_1ep_nofs` entry (folder `qwen_lora_no_few_shots`, `use_few_shot: false`, `num_epochs: 1`) for both 3B and 7B; the script selects runs by `use_few_shot == false` at each epoch count so it doesn't silently pick the few-shot variant.
  - Building `compare_few_shots_to_excel.py` surfaced two data bugs in the old hand-assembled `few_shots_ablation.xlsx` (3B sheet only): the `qwen_base` block's `enes`/`enru` term-accuracy values were swapped between rows, and both the `qwen_base` and `qwen_lora` blocks' 3rd row was labeled `ende` instead of `enru` (values were correct in the `qwen_lora` block — label-only typo there; the `qwen_base` block had the actual value swap). **Fixed** — the generated file derives each row directly from `metrics_summary.json` per language, so this can't recur. It also fills `Qwen2.5-7B`'s `qwen_base` `no_shots` cells, which the old file left blank even though `results/dev_v1/original/no-few-shots/qwen_7b/metrics_summary.json` exists.

## 3. Undocumented or partially-documented experiments

- **"Good vs bad data" leakage honesty check** (see `README.md` §3.4.2 for the full reconstruction) — not mentioned in any README anywhere in the repo. Only visible via `experiments/04_lora_finetuning/report/good vs bad data.xlsx` (formerly a sheet inside `comparisons.xlsx`, now its own file) and its partial generator script `fill_good_vs_bad_gpt.py` (path updated to point at the new file).
  - **Bug found:** `fill_good_vs_bad_gpt.py`'s Qwen-base block wires `good_path` to the plain, unfiltered `qwen_base/metrics_summary.json` — not an actual good-filtered subset. So the Qwen-base row of the sheet is silently "bad-filtered vs. full-unfiltered," not "good vs bad" like the GPT row and the (separately, manually entered) LoRA rows. **This makes the Qwen-base row in the current sheet directly misleading if cited as-is.** (Not fixed as part of the report-file rename — only the file path was updated, this labeling bug is still open.)
  - Only 2 of 5 comparison blocks (GPT, Qwen-base) are script-generated; the 3 `qwen_lora` blocks have no generating script anywhere and appear hand-entered.
  - Only evaluated for Qwen **7B**; no 3B good/bad results exist.
  - `filter_test_sentence_overlap.py` / `filter_test_term_overlap.py` both default to output directories (`data/test_cleaned_gpt`, `data/test_cleaned`) that don't match the actually-committed directories (`test_cleaned_by_sentences/`, `test_cleaned_by_terms/`) — as committed, neither script reproduces the current data without manually passing `--output-dir`.
  - `filter_test_term_overlap.py` overwrites its input file in place (per subagent investigation) — re-running it destructively modifies source data rather than writing a fresh copy, unlike its sentence-level sibling.

- **`test_cleaned_by_terms` split prepared but never evaluated**, and turns out heavily skewed once inspected: 11–14 "good" sentences vs. 483–486 "bad" sentences per language (nearly every dev_v1 sentence shares a term-dictionary entry with dev_v2 training data). No `results/.../test_cleaned_by_terms/` directory exists anywhere.
  - **Recommendation:** don't run it — note the skew as the reason it wasn't used, rather than silently omitting it.

- **Few-shot is split across two independently-produced, inconsistently-named result trees**, unified only inside `experiments/04_lora_finetuning/scripts/figure_lora_finetuning.py`:
  1. Baseline-level: `results/dev_v1/original/{no-few-shots,with-few-shots}/` (repo root) — GPT + Qwen 3B/7B, no fine-tuning. **Status: fixed** — both subfolders now consistently use `qwen_3b`/`qwen_7b` (underscore); `no-few-shots/` previously used `qwen-3b`/`qwen-7b` (hyphen). Internal directory shape still differs between the two (unrelated, not fixed here).
  2. LoRA-level: `run_registry.json`'s `lora_1ep_fs` is the only few-shot LoRA run; all multi-epoch runs are no-few-shot — so on the LoRA side, "few-shot effect" and "epoch count" are confounded. There is no `lora_2ep_fs`/`lora_3ep_fs` to isolate them.
  3. **`run_registry.json`'s `use_few_shot: false` for both Qwen base runs is itself wrong** — the actual 7B base run used 3 few-shot examples per language (confirmed by `comparisons.xlsx`'s own column header `qwen_base_with_few_shots`, and by the notebook's `SAMPLE_SENTENCES`/`USE_FEW_SHOT` logic). `metrics_parser.py` only falls back to the registry flag when a run's `metrics_summary.json` predates the `use_few_shot` field — which is exactly the base runs' case, so the wrong flag silently propagates into any table built from the registry.
  - **Fix:** correct the registry's `use_few_shot` flags for both base runs (still open); decide (see §6) whether to invest in the missing `lora_2ep_fs`/`lora_3ep_fs` runs or explicitly describe the confound as a limitation (still open).

## 4. Excel workbook mess

- **`experiments/01_term_expansion_by_model/report/dev_v1_original_model_comparison.xlsx` has 3 sheets** (`metrics`, `Sheet1`, `terms expansion types`) where its 3 sibling files (`dev_v1_cleaned_...`, `dev_v1_expand_...`, `dev_v2_...`) each have exactly 1 sheet (`metrics`). `Sheet1` is openpyxl's un-renamed default sheet name, containing a near-duplicate table (headed `data` instead of `mode`, extra Term-Accuracy columns) — leftover scratch output. `terms expansion types` is a third, differently-shaped table. Neither extra sheet is mentioned in the README.
  - **Fix:** delete `Sheet1` and `terms expansion types` from this one file (or fold their unique content into `metrics` if anything in them isn't already redundant), so all 4 sibling files have the same, single-sheet shape. Cite only the `metrics` sheet until then.

- **`experiments/02_term_expansion_by_language_pair/report/dev_v1_original_mode_comparison.xlsx` has a different internal layout than its 3 siblings.** All 4 files have exactly 1 sheet named `modes`, but the 3 siblings (`dev_v1_cleaned_...`, `dev_v1_expand_...`, `dev_v2_...`) are each an 11-row wide table, while `dev_v1_original_...` is 51 rows: a title row `'Original data'` followed by four stacked long-format blocks (Original / Expand / Cleaned / devset_2) — effectively cramming what the other three files keep as separate per-variant files into one sheet, in a different shape.
  - **Fix:** decide whether `dev_v1_original_mode_comparison.xlsx` should be reshaped to match its siblings (1 wide table) or whether the siblings are the ones that should be consolidated to match it — right now the four "identically named" files are not structurally comparable, which will bite whoever writes the table-generation code for the paper.
  - **Note:** the generating script has since been repivoted and renamed — `compare_modes_to_excel.py` (mode columns, model×language rows) is now [`compare_languages_to_excel.py`](../experiments/02_term_expansion_by_language_pair/scripts/compare_languages_to_excel.py) (language columns, mode×model rows), writing `<dataset>_language_comparison.xlsx`. The 4 on-disk `*_mode_comparison.xlsx` files described above are stale outputs of the old script and haven't been regenerated under the new name/shape yet — this fix should happen as part of that regeneration, not by patching the old files.

- **`_x0009_` sheet-name corruption in `comparisons.xlsx`.** — ✅ fixed. `qwen_lora_with_no_few_shots_x0009_` and `qwen_lora_no_few_shots_n_epoch_x0009_` contained a literal `_x0009_`, openpyxl's escape for an embedded raw TAB character — someone hit Tab while renaming an Excel sheet tab and it got baked into the name. `comparisons.xlsx` has since been deleted and split into 5 separate files with clean sheet names (`Sheet1`, `Qwen2.5-3B`, `Qwen2.5-7B`, `GPT-4o-mini`, `good vs bad data` — no `_x0009_` anywhere), so this no longer applies.

- **Mixed autogenerated/hand-edited sheets with no record of which cells are which.** `best_models.xlsx` and `good vs bad data.xlsx` (successors to `comparisons.xlsx`'s `best-models` and `good vs bad data` sheets) mix script-written cells (GPT, Qwen-base blocks, in `good vs bad data.xlsx` only) with hand-entered ones (LoRA blocks) with no marker distinguishing them — see §3.
  - **Fix going forward:** either script-generate every cell (write the missing `qwen_lora` block generator) or clearly flag hand-edited sheets/cells (e.g. a header note or a distinct fill color) so a reader — or the report writer six months later — can tell which numbers are traceable to a script run and which aren't.
